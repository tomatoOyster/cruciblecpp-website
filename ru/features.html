проверяемым поведением

От выбора целевой версии, предопределённых макросов и диагностики до PCH и реальных проектов: CrucibleCpp работает не на «должно работать», а на воспроизводимой цепочке тестов.

A

Целевая версия и профиль

Один препроцессор — три целевых GCC. Для выбранной версии используются её предопределённые макросы, данные __has_* и пути поиска include.

  • --gcc-version=13|14|15
  • --gcc D:\path\to\g++.exe
  • Автоопределение в PATH, по умолчанию выбирается максимальная поддерживаемая версия
  • GCC 13.3 / 14.3 / 15.2 profile
  • C++11 / C++14 / C++17 / C++20
B

Система диагностики

Формат диагностики для реальных систем сборки. Включает строку исходника, caret, include trace и warning option, а не просто строку ошибки.

  • Стиль GCC: severity / option / caret
  • -Werror, -Wno-..., -Werror=...
  • #pragma GCC diagnostic push/pop
  • #pragma GCC system_header
  • -Wsystem-headers и подавление системных заголовков
C

Макросы и семантика препроцессирования

Объектные и функциональные макросы, пустые аргументы, вариативные макросы, строкификация, token pasting и расширение GCC по удалению запятых.

  • # и ##
  • __VA_OPT__(C++20)
  • , ## __VA_ARGS__
  • defined / __has_include
  • JSON с macro trace и анализом графа include
D

UCN и #embed

Универсальные имена символов участвуют в идентификаторах и склейке; #embed встраивает двоичные ресурсы по семантике GCC.

  • \uXXXX / \UXXXXXXXX
  • UCN, образованные обратным слешем и переводом строки
  • # / ## не меняют написание UCN
  • #embed + limit
  • prefix / suffix / if_empty
  • gnu::offset и __has_embed
E

PCH и кэширование

В GCC 13/14/15 доступны стратегии PCH и кэш. Кэш не разбирает PCH GCC напрямую, а проверяет, регистрирует, инвалидирует и отслеживает внешние .gch.

  • --pch=ignore|warn|error|report
  • Раскладка CMake PCH с принудительным include
  • Изоляция по пути к компилятору, версии и хешу
  • Атомарная запись, блокировки каталогов, очистка по объёму и возрасту
  • JSON-статистика попаданий / stale / corrupt
F

Воспроизводимые тесты

Три набора GCC, два дифференциальных корпуса и реальные проекты совместно проверяют вывод, а не только «успешное препроцессирование».

  • GCC15 / 14 / 13 — по 65/65 CTest
  • differential corpus 13/13
  • realworld corpus 3/3
  • CrucibleCpp .i → целевой GCC → exe → запуск
  • GCC g++.dg/cpp Регрессия testsuite
Positioning

Он заменяет этап препроцессирования, а не компилятор

CrucibleCpp не генерирует код, не выполняет оптимизацию и не разбирает двоичные PCH GCC. Его задача — превратить исходные файлы в детерминированный .i, передавая диагностику, зависимости и данные для анализа системе сборки.
