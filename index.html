Why CrucibleCpp

不是另一个宏展开器，
而是可验证的预处理层

每个正例都经过同一条链路：CrucibleCpp 生成 .i，对应 GCC 编译成 exe，再实际运行。行为以 GCC 15.2、14.3、13.3 为基准。

01

目标版本明确

用 --gcc-version 或 --gcc 选择目标编译器。profile、内置宏和 include 路径来自同一个目标，不混用。

02

GCC 诊断对齐

源码 caret、include trace、warning ID、-Werror、pragma diagnostic 栈，以及系统头的警告抑制。

03

真实项目验证

nlohmann/json、fmt、spdlog 在三个 GCC 版本上完成预处理、编译和运行，覆盖真实头文件与宏组合。

04

完整 UCN

\uXXXX 与 \UXXXXXXXX 参与标识符、#、##；合法性检查和输出规范化与 GCC 对齐。

05

#embed

二进制嵌入、limit、gnu::offset、prefix、suffix、if_empty，以及 __has_embed。

06

PCH 版本隔离

GCC 13 / 14 / 15 的 PCH 策略和缓存都可用。manifest 记录编译器路径、版本和可执行文件哈希，避免跨版本误命中。

Compatibility

从一个明确的矩阵开始

当前生产目标锁定 Windows x64 + MinGW-w64 UCRT64。不同 GCC 版本使用各自的 profile 和头文件，输出由对应 GCC 实际编译验证。

Test chain

验证不是“看起来能跑”

  • GCC15 / 14 / 13 三套 CTest，各自 65/65
  • differential corpus 13/13：退出码、诊断、token 流
  • realworld corpus 3/3：nlohmann/json、fmt、spdlog
  • 每个正例生成 exe 后实际运行
  • PCH policy 与 cache 在三个版本上通过
  • GCC g++.dg/cpp testsuite 持续回归
