Capabilities

हर परत को
सत्यापनीय व्यवहार बनाएँ

लक्ष्य संस्करण के चयन, पूर्वनिर्धारित मैक्रो और निदान से लेकर PCH और वास्तविक परियोजनाओं तक, CrucibleCpp “चल जाना चाहिए” पर नहीं, बल्कि दोहराए जा सकने वाली परीक्षण-श्रृंखला पर निर्भर है।

A

लक्ष्य संस्करण और प्रोफ़ाइल

एक प्रीप्रोसेसर, तीन लक्ष्य GCC। जिस संस्करण को चुनें, उसी संस्करण के पूर्वनिर्धारित मैक्रो, __has_* डेटा और include खोज पथ उपयोग होते हैं।

  • --gcc-version=13|14|15
  • --gcc D:\path\to\g++.exe
  • PATH से स्वतः पहचान, डिफ़ॉल्ट रूप से उच्चतम समर्थित संस्करण चुना जाता है
  • GCC 13.3 / 14.3 / 15.2 profile
  • C++11 / C++14 / C++17 / C++20
B

निदान प्रणाली

वास्तविक बिल्ड सिस्टम के लिए बना निदान प्रारूप। इसमें स्रोत पंक्ति, caret, include trace और warning option शामिल हैं, केवल एक त्रुटि स्ट्रिंग नहीं।

  • GCC शैली severity / option / caret
  • -Werror, -Wno-..., -Werror=...
  • #pragma GCC diagnostic push/pop
  • #pragma GCC system_header
  • -Wsystem-headers और सिस्टम हेडर का दमन
C

मैक्रो और प्रीप्रोसेसिंग सिमैंटिक्स

ऑब्जेक्ट मैक्रो, फ़ंक्शन मैक्रो, रिक्त आर्ग्युमेंट, वेरिएडिक मैक्रो, स्ट्रिंगिफ़िकेशन, token pasting, और GCC का कॉमा-हटाने वाला एक्सटेंशन।

  • # और ##
  • __VA_OPT__(C++20)
  • , ## __VA_ARGS__
  • defined / __has_include
  • macro trace और include ग्राफ़ विश्लेषण JSON
D

UCN और #embed

Universal character name पहचानकर्ताओं और टोकन जोड़ाई में भाग लेते हैं; #embed GCC के अनुसार बाइनरी संसाधन एम्बेड करता है।

  • \uXXXX / \UXXXXXXXX
  • बैकस्लैश-न्यूलाइन से बनी UCN
  • # / ## में UCN की मूल वर्तनी सुरक्षित रहती है
  • #embed + limit
  • prefix / suffix / if_empty
  • gnu::offset और __has_embed
E

PCH और कैश

GCC 13/14/15 तीनों PCH रणनीति और कैश का उपयोग कर सकते हैं। कैश GCC के PCH को सीधे पार्स नहीं करता, बल्कि बाहरी फ़ाइलों को सत्यापित, पंजीकृत, अमान्य और ट्रैक करता है — .gch.

  • --pch=ignore|warn|error|report
  • जबरन include वाला CMake PCH लेआउट
  • compiler पथ, संस्करण और हैश का अलगाव
  • परमाणु लेखन, निर्देशिका लॉक, क्षमता और आयु के आधार पर सफ़ाई
  • हिट दर / stale / corrupt आँकड़े JSON
F

पुनरुत्पादनीय परीक्षण

तीन GCC सेट, दो differential corpus और वास्तविक परियोजनाएँ मिलकर आउटपुट सत्यापित करते हैं, केवल “प्रीप्रोसेसिंग सफल” का परीक्षण नहीं करते।

  • GCC15 / 14 / 13 प्रत्येक 65/65 CTest
  • differential corpus 13/13
  • realworld corpus 3/3
  • CrucibleCpp .i → लक्ष्य GCC → exe → रन
  • GCC g++.dg/cpp testsuite रिग्रेशन
Positioning

यह प्रीप्रोसेसिंग चरण का स्थान लेता है, कंपाइलर का नहीं

CrucibleCpp कोड जनरेशन, अनुकूलन या GCC के बाइनरी PCH को पार्स करने का काम नहीं करता। इसका काम केवल स्रोत फ़ाइलों को एक नियतात्मक .i में बदलना और निदान, निर्भरताएँ तथा विश्लेषण-योग्य जानकारी बिल्ड सिस्टम को सौंपना है।
