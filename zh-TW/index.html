Why CrucibleCpp

不是另一個巨集展開器，
而是可驗證的預處理層

每個正例都經過同一條流程：CrucibleCpp 產生 .i，由對應的 GCC 編譯成 exe，再實際執行。行為以 GCC 15.2、14.3、13.3 為基準。

01

目標版本明確

用 --gcc-version 或 --gcc 選擇目標編譯器。profile、內建巨集與 include 路徑皆來自同一個目標，不混用。

02

GCC 診斷對齊

原始碼 caret、include trace、warning ID、-Werror、pragma diagnostic 堆疊，以及系統標頭檔的警告抑制。

03

真實專案驗證

nlohmann/json、fmt、spdlog 在三個 GCC 版本上完成預處理、編譯與執行，涵蓋真實標頭檔與巨集組合。

04

完整 UCN

\uXXXX 與 \UXXXXXXXX 參與識別字、#、##；合法性檢查與輸出正規化皆與 GCC 對齊。

05

#embed

二進位內嵌、limit、gnu::offset、prefix、suffix、if_empty，以及 __has_embed。

06

PCH 版本隔離

GCC 13 / 14 / 15 的 PCH 策略與快取皆可使用。manifest 會記錄編譯器路徑、版本與執行檔雜湊，避免跨版本誤命中。

Compatibility

從明確的矩陣開始

目前生產目標鎖定 Windows x64 + MinGW-w64 UCRT64。不同 GCC 版本使用各自的 profile 與標頭檔，輸出由對應的 GCC 實際編譯驗證。

目標狀態說明
GCC 15.2完整C++11/14/17/20 profile
GCC 14.3完整C++11/14/17/20 profile
GCC 13.3完整C++11/14/17/20 profile
Windows x64 / UCRT64支援目前生產目標
Linux / MSVC / Clang未支援架構保留擴充點
Test chain

驗證不是「看起來能跑」

  • GCC15 / 14 / 13 三套 CTest，各自 65/65
  • differential corpus 13/13：結束代碼、診斷、token 串流
  • realworld corpus 3/3：nlohmann/json、fmt、spdlog
  • 每個正例產生 exe 後皆實際執行
  • PCH policy 與 cache 在三個版本上通過
  • GCC g++.dg/cpp testsuite 持續回歸
