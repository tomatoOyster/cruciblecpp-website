Why CrucibleCpp

Not another macro expander,
but a verifiable preprocessing layer

Every positive case goes through the same chain: CrucibleCpp generates .i, which the matching GCC compiles into an exe and then actually runs. Behavior is benchmarked against GCC 15.2, 14.3, and 13.3.

01

Explicit target versions

Use --gcc-version or --gcc to select the target compiler. The profile, built-in macros, and include paths all come from the same target and are never mixed.

02

GCC diagnostic parity

source caret, include trace, warning ID,-Werror, the pragma diagnostic stack, and suppression of system-header warnings.

03

Validated on real projects

nlohmann/json, fmt, and spdlog are preprocessed, compiled, and run on all three GCC versions, covering real headers and macro combinations.

04

Full UCN

\uXXXX and \UXXXXXXXX participate in identifiers,#, ##; validity checks and output normalization are aligned with GCC.

05

#embed

binary embedding,limit, gnu::offset, prefix, suffix, if_empty, and __has_embed.

06

PCH version isolation

PCH strategies and caches are available for GCC 13 / 14 / 15. The manifest records the compiler path, version, and executable hash so that caches never produce false hits across versions.

Compatibility

Start with an explicit matrix

The current production target is locked to Windows x64 + MinGW-w64 UCRT64. Each GCC version uses its own profile and headers, and the output is verified by actually compiling it with the matching GCC.

Test chain

Verification is not “it looks like it runs”

  • Three CTest suites for GCC 15 / 14 / 13, each 65/65
  • differential corpus 13/13: exit codes, diagnostics, and token streams
  • realworld corpus 3/3: nlohmann/json, fmt, spdlog
  • Every positive case is actually run after its exe is built
  • PCH policy and cache pass on all three versions
  • GCC g++.dg/cpp testsuite regression runs continuously
